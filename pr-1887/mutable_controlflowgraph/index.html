    Modify a ControlFlowGraph

    The goal

    The (fictional) bank SootBank ships a class Vault whose withdraw method was written in a hurry:

     1
 2
 3
 4

    /** A fictional vault whose withdraw method gets hardened in the "Modify a ControlFlowGraph" docs. */
public class Vault {
  private int balance = 100;

  public int withdraw(int amount) {
    Legacy.check(amount);
    System.out.println(amount);
    balance = balance - amount;
    return balance;
  }
}

    An audit lists four problems, and nobody has access to the sources any more, only to the .class files. We will fix all of them in the ControlFlowGraph of the method:

    1. every call must be logged: Audit.log(amount) at the very beginning,
    2. Legacy.check is insecure and must be replaced by Secure.check,
    3. the leftover debug output System.out.println must be removed,
    4. non-positive amounts must be rejected (return -1),
    5. a RuntimeException during the withdrawal must be caught, reported via Audit.failed(e) and answered with return -1.

    Each requirement needs a different kind of modification, so step by step this chapter walks through the API of MutableControlFlowGraph. At the end we pack everything into a BodyInterceptor, so every view loads the hardened method automatically.

    All code on this page is taken from sootup.examples/src/test/java/sootup/examples/mutatingCFG, which is run as a test on every pull request.

    A ControlFlowGraph can be read on two levels:

    • Stmts: successors(stmt), predecessors(stmt), exceptionalSuccessors(stmt), getStmts() (in Jimple order), getStartingStmt(), containsNode(stmt).
    • Blocks: a BasicBlock is a maximal sequence of stmts that is always executed from head to tail. Only the tail may branch, and all stmts of a block share the same exceptional successors. getBlocks(), getBlockOf(stmt), getBlocksSorted().

Collection<? extends BasicBlock<?>> blocks = cfg.getBlocks();
BasicBlock<?> blockOfFirst = cfg.getBlockOf(first);

    withdraw has no branches and no traps, so its graph is a single block.

    Falls through or branches?

    Every Stmt is either a FallsThroughStmt (it continues with the next stmt, e.g. an assignment or an invoke), a BranchingStmt (goto, switch) or it ends the flow (return, throw). JIfStmt is both: its successor 0 is the fall-through flow, its successor 1 the branch target. Many modification methods only accept one of these kinds, and the types in their signatures say which.

    Step 1 — Get a mutable copy

    The graph of a loaded Body is unmodifiable. Body.builder(body, modifiers) copies the body into a BodyBuilder, whose graph is a MutableBlockControlFlowGraph:

    1
2
    Body.BodyBuilder builder = Body.builder(body, withdraw.getModifiers());
MutableControlFlowGraph graph = builder.getControlFlowGraph();

    The copy shares the Stmt objects with the original body, but not the graph. Whatever we change from now on leaves body untouched.

    Step 2 — Insert: log every call

    insertBefore(existing, stmts...) puts new stmts in front of existing. All flows that reached existing now reach the first new stmt. insertAfter(existing, stmts...) works the other way round. Both accept only FallsThroughStmts that are no JIfStmt, because the inserted stmts always continue into existing or into its old successor.

    The log call has to come after the identity stmts (this := @this, l1 := @parameter0), which must stay at the beginning of a body:

    1
2
3
4
5
6

    Local amount = body.getParameterLocal(0);
MethodSignature auditLog = factory.parseMethodSignature("<Audit: void log(int)>");
JInvokeStmt logCall =
    Jimple.newInvokeStmt(Jimple.newStaticInvokeExpr(auditLog, amount), NO_POS);
// before the first "real" stmt, i.e. after this := @this and amount := @parameter0
Stmt firstNonIdentity = body.getFirstNonIdentityStmt();
graph.insertBefore(firstNonIdentity, logCall);

    Both methods also take a list of stmts and a trap map Map<ClassType, Stmt> (exception type → handler stmt) for the new stmts. The single-stmt overloads used here pass an empty map, so the new stmts are covered by no trap. Pass the traps of the neighbouring stmt (graph.exceptionalSuccessors(existing)) if the new stmts belong into the same try block.

    Step 3 — Replace: swap the insecure check

    replaceNode(old, new) puts new at the place of old. All flows into and out of old move to new, and so do its traps.

    1
2
3
4
5
6
7
    JInvokeStmt legacyCheck = invokeOf(graph, "check");
MethodSignature secureCheck = factory.parseMethodSignature("<Secure: void check(int)>");
JInvokeStmt secureCall =
    Jimple.newInvokeStmt(
        Jimple.newStaticInvokeExpr(secureCheck, legacyCheck.getInvokeExpr().get().getArgs()),
        NO_POS);
graph.replaceNode(legacyCheck, secureCall);

    One stmt, one place

    Stmts are compared by identity, and a stmt object can be in a graph only once. Always create a new stmt instead of reusing one: replaceNode and all insert methods reject a stmt that is already in the graph.

    replaceNode can also change the kind of a stmt, e.g. goto → nop or nop → goto. When the new stmt expects fewer successors than the old one still has, it throws. Flows that are missing after the replacement (e.g. the target of a new goto) are added with the edge methods of step 5.

    Step 4 — Remove: drop the debug output

    removeNode(stmt) removes a stmt and keeps the flow: its predecessors now continue with its successor. removeNode(stmt, false) removes the stmt together with its flows, which may leave a part of the graph unreachable. Keeping the flow is impossible for a BranchingStmt with more than one successor.

    println needs a second stmt that loads System.out, so we remove both. The local that held System.out is unused afterwards, and we remove it from the builder as well:

locals.remove(((JAssignStmt) loadSystemOut).getLeftOp());
builder.setLocals(locals);

    To remove a whole block, use removeBlock(block).

    Step 5 — Change the flow: a guard clause

    Now the method needs a branch: if l1 <= 0 goto reject, where reject is a new return -1. This is a job for the edge methods:

    Method Effect
    putEdge(FallsThroughStmt from, Stmt to) from falls through into to. A to that is not in the graph yet is added, with the traps of from.
    putEdge(BranchingStmt from, int idx, Stmt to) sets successor idx of from
    setEdges(BranchingStmt from, Stmt... targets) sets all successors of from at once, in order
    removeEdge(Stmt from, Stmt to) removes all flows from → to and returns their successor indices
    replaceSuccessorEdge(Stmt from, Stmt oldTo, Stmt newTo) redirects all flows from → oldTo to newTo
    addNode(Stmt) / addNode(Stmt, traps) adds a stmt without any flow
    addBlock(List<Stmt>) / addBlock(List<Stmt>, traps) adds a whole sequence of stmts
    setStartingStmt(Stmt) sets the entry of the method

    A FallsThroughStmt has exactly one fall-through successor, so before the log call can fall through into the guard, we cut its current flow:

     1

    // if amount <= 0 goto reject;  reject: return -1
JIfStmt guard = Jimple.newIfStmt(Jimple.newLeExpr(amount, IntConstant.getInstance(0)), NO_POS);
JReturnStmt reject = Jimple.newReturnStmt(IntConstant.getInstance(-1), NO_POS);

Stmt afterLog = graph.successors(logCall).get(0);
graph.removeEdge(logCall, afterLog); // cut the fall-through flow
graph.putEdge(logCall, guard); // logCall falls through into the new guard
// successor 0 of an if is its fall-through flow, successor 1 its branch target
graph.putEdge(guard, JIfStmt.FALSE_BRANCH_IDX, afterLog);
graph.putEdge(guard, JIfStmt.TRUE_BRANCH_IDX, reject);

    The two putEdge(guard, ...) calls could also be written as graph.setEdges(guard, afterLog, reject). For a switch, the successor indices follow the order of its cases, and the default target comes last.

    The method now consists of three blocks: entry up to the guard, the withdrawal, and reject.

    Step 6 — Exceptional flow: catch a RuntimeException

    In a ControlFlowGraph an exceptional flow goes from a stmt to the handler stmt for one exception type. A handler is a block that starts with e := @caughtexception. The trap ranges (catch ... from ... to ... with ...) you see in Jimple are computed from these flows when the body is printed or serialized.

    We add the handler as a new block, then give every stmt after the guard an exceptional flow into it:

    ClassType runtimeException = factory.getClassType("java.lang.RuntimeException");
MethodSignature auditFailed =
    factory.parseMethodSignature("<Audit: void failed(java.lang.RuntimeException)>");

// the handler:  e := @caughtexception; Audit.failed(e); return -1
Local e = Jimple.newLocal("e", runtimeException);
builder.addLocal(e);
JIdentityStmt caught =
    Jimple.newIdentityStmt(e, new JCaughtExceptionRef(runtimeException), NO_POS);
JInvokeStmt reportFailure =
    Jimple.newInvokeStmt(Jimple.newStaticInvokeExpr(auditFailed, e), NO_POS);
JReturnStmt failed = Jimple.newReturnStmt(IntConstant.getInstance(-1), NO_POS);
graph.addBlock(Arrays.asList(caught, reportFailure, failed));

// every stmt between the guard and the return may throw into the handler
Stmt debit = afterLog;
while (!(debit instanceof JReturnStmt)) {
  Stmt following = graph.successors(debit).get(0);
  graph.addExceptionalEdge(debit, runtimeException, caught);
  debit = following;
}

    Note the following variable: we read the successor before changing the graph, because the graph may restructure its blocks while we edit (see the rules below).

    The way back works at three granularities:

    public class VaultHardeningInterceptor implements BodyInterceptor {

  private static final StmtPositionInfo NO_POS = StmtPositionInfo.getNoStmtPositionInfo();

  @Override
  public void interceptBody(Body.@NonNull BodyBuilder builder, @NonNull View view) {
    MethodSignature sig = builder.getMethodSignature();
    if (!sig.getDeclClassType().getFullyQualifiedName().equals("Vault")
        || !sig.getName().equals("withdraw")) {
      return;
    }
    MutableControlFlowGraph graph = builder.getControlFlowGraph();
    graph.beginBatch();
    try {
      harden(builder, graph, view);
    } finally {
      graph.endBatch();
    }
  }

    // harden(...) contains the steps 2 – 6 from above
}

    It is registered on the input location after the default interceptors:

    1
    JavaView view = loadView(Collections.singletonList(new VaultHardeningInterceptor()));

    Many edits: batch mode

    The interceptor wraps its edits in beginBatch() / endBatch() of MutableControlFlowGraph. After each edit, a MutableBlockControlFlowGraph merges blocks that became mergeable, so that blocks stay maximal. During a sequence of edits that often means splitting and merging the same blocks again and again. Inside a batch, merging is postponed until the outermost endBatch(). The stmt-level flows are exact during the batch, only getBlocks() may return more, smaller blocks than necessary. Batches can be nested. Put endBatch() in a finally block. Other MutableControlFlowGraph implementations treat both calls as no-ops, so the pattern is always safe.

    Changing a single method without an interceptor

    To replace the body of one SootMethod in an existing view, wrap the new body into an OverridingBodySource and create a new method with withOverridingMethodSource; see sootup.examples/.../mutatingSootClass/MutatingTest.java.

    Rules of the graph

    • Only a block's tail may branch. Stmts inside a block fall through. The graph splits and merges blocks for you.
    • One fall-through successor. A FallsThroughStmt falls through into exactly one stmt. For the body to be printable as linear code, a stmt should also be the fall-through target of at most one stmt; connect further predecessors with a goto. A fall-through cycle (a falls into b, b into a) can never be linearized and is rejected.
    • New stmts, always. A stmt object can be in a graph only once.
    • The starting stmt is a block head. It changes with setStartingStmt, or when you insert before or remove the first stmt.
    • Keep Stmts, not BasicBlocks. Blocks are split and merged by almost every modification, so a block you got before an edit may be outdated after it. Look it up again with getBlockOf(stmt).
    • Iterate over a copy. getStmts() returns a new list, so you can change the graph while you loop over it. When you walk along successors(...), read the next stmt before you change the current one (see step 6).
    • Invalid arguments fail early. An invalid edit throws an IllegalArgumentException and does not change the graph. MutableBlockControlFlowGraph.validateBlocks() checks the internal consistency, which is handy while debugging your own transformation.

    Costs

    Operation Cost
    getBlockOf, successors, predecessors, containsNode O(1)
    insert/remove at the head or tail of a block, replaceNode O(1) plus the edge changes
    insert/remove in the middle of a block proportional to the shorter part of the block
    split/merge of a block proportional to the smaller part
    getStmts() O(n) copy; the order is cached and survives changes inside a block
    copy constructor O(n)
    initializeWith O(n), plus a split for every branch target that is not the head of a given block
