    Call Graphs: a Step-by-Step Tutorial

    A call graph records which methods a program may call. Its nodes are methods. Each edge is one call: a caller, a callee, and the invoke statement in the caller that makes the call (CallGraph.Call). Most interprocedural analyses need a call graph, e.g. the taint analysis and the typestate analysis.

    The hard part is the virtual call. For shape.area() the compiler only knows the static type Shape, so a call graph algorithm has to estimate which area() implementations can run there. Algorithms differ in how precise that estimate is and how much it costs. This tutorial uses one small program to show the difference, then walks through every configuration option.

    All code on this page comes from tests in sootup.examples/src/test/java/sootup/examples/callgraph/. It compiles, and it does what the comments say.

    Dependencies

    CHA and RTA are in sootup.callgraph. Spark needs sootup.spark, and Qilin needs sootup.qilin. See Installation.

    Step 1: Load the program into a View

    Every algorithm works on a View. Add the program under analysis as an application input location, and the Java runtime as a library input location:

    1
2
3
4
5
6
7
8
    List<AnalysisInputLocation> inputLocations =
    List.of(
        // the program under analysis: SourceType.Application
        new JavaClassPathAnalysisInputLocation(
            "src/test/resources/CallgraphComparison/binary", SourceType.Application),
        // the JDK of the running JVM: SourceType.Library
        new DefaultRuntimeAnalysisInputLocation());
JavaView view = new JavaView(inputLocations);

    The runtime is needed because every program calls into the JDK, even if only Object.<init>(). Without it, those targets can't be resolved. By default, the algorithms record calls into library methods but don't analyze library method bodies. callResolver changes that.

    Step 2: Choose the entry points

    A call graph starts at one or more entry methods and contains everything reachable from them. For an application, the entry point is usually main:

    1
2
3
4
    ClassType mainClass = view.getIdentifierFactory().getClassType("Main");
MethodSignature mainMethod =
    view.getIdentifierFactory()
        .getMethodSignature(mainClass, view.getIdentifierFactory().getMainSubSignature());

    You can also parse the signature from a string:

    1
2
    MethodSignature mainMethod =
    view.getIdentifierFactory().parseMethodSignature("<Main: void main(java.lang.String[])>");

    Any method can be an entry point, e.g. every public method of a library, or the handler methods of a framework. If you pass no entry points, CHA and RTA start from every main(String[]) method of the application.

    Step 3: Pick an algorithm

    The running example

    1
2
3
    public interface Shape {
  double area();
}

    Circle, Square, Triangle and Hexagon implement Shape. Each area() returns a constant.

     1
 2
 3

    public class Main {

  static Shape id(Shape s) {
    return s;
  }

  public static void main(String[] args) {
    Shape circle = new Circle();
    circle.area(); // call site 1

    Shape triangle = id(new Triangle()); // the result is never used
    Shape square = id(new Square());
    square.area(); // call site 2
  }
}

    At run time, call site 1 (line 9) calls Circle.area() and call site 2 (line 13) calls Square.area(). Nothing else is ever called. This is what each algorithm computes:

    Algorithm Call site 1 circle.area() Call site 2 square.area() Reasoning
    CHA Circle, Square, Triangle, Hexagon Circle, Square, Triangle, Hexagon Every class that implements Shape
    RTA Circle, Square, Triangle Circle, Square, Triangle Only classes that the program instantiates with new somewhere. Hexagon is gone
    Spark, Qilin insensitive() Circle Square, Triangle Only objects that can actually flow into the variable. Both new Triangle() and new Square() pass through id(), which is analyzed once, so its return value may be either
    Qilin callSite(1) Circle Square id() is analyzed separately for each call site, so id(new Square()) returns only a Square. Exact

    From top to bottom, the algorithms get more expensive and more precise. Every algorithm over-approximates: it may report calls that never happen, but it doesn't miss calls the program makes (within the limits of static analysis). Every extra edge makes the analyses built on top of the call graph slower and less precise. For example, a taint analysis on the CHA graph would also track flows through Hexagon.area().

    CallGraphComparisonTest asserts exactly this table.

    More context is not automatically more precision

    Which kind of context helps depends on the code. id() is static, so it has no receiver object. An object-sensitive analysis (ContextSensitivity.objectSensitive(2, 1)) therefore has no context to tell the two id(...) calls apart, and reports Square and Triangle at call site 2, just like the context-insensitive analysis. A call-site-sensitive analysis distinguishes the two calls by their call sites. For code that routes objects through instance methods (getters, containers, builders), object sensitivity is usually the better choice.

    Which one should I use?

    • CHA: start here. Fast and simple, and it needs no knowledge about objects. Also the base graph for Spark.
    • RTA: almost as fast as CHA, and usually noticeably smaller. A good default for whole-program analyses.
    • Spark: context-insensitive points-to analysis. Use it when you also need points-to sets, or when RTA is too imprecise.
    • Qilin: the full range of context-sensitive points-to analyses. Use it when precision matters more than run time.

    Step 5: Shared options

    These options go on CallGraphConfig.builder() before you choose the family. The examples use CHA. The other families support the same options, with the exceptions listed in Which family uses which option.

    callResolver: which methods get analyzed

    A CallResolver is asked once for every method the algorithm reaches, before the method's body is loaded. It returns a CallFilter that decides which calls in the method get resolved:

    • CallFilter.all(): every call.
    • CallFilter.none(): no call. The body is not even loaded. The method stays in the call graph as a node, but has no outgoing edges.
    • CallFilter.of(stmt -> ...): only the calls in statements the predicate accepts.

    The default is DefaultCallResolver. It returns none() for library methods, so the JDK is not analyzed:

    1
2
3
4

    CallGraph cg =
    CallGraphConfig.builder()
        .view(view)
        .entryPoints(List.of(mainMethod))
        .callResolver(new DefaultCallResolver(view)) // the default: don't look into the JDK
        .cha()
        .build()
        .computeCallGraph();

    To analyze library methods too (this can make the graph, and the run time, much bigger):

    Excluding a method only removes its outgoing edges

    A CallResolver only decides whether a method's own calls get resolved. Calls into the method from other methods stay in the call graph.

    virtualCallResolver: which resolved targets to keep

    A VirtualCallResolver is asked after a call has been resolved, once per possible target. That includes the static initializers (<clinit>) that the call triggers. It returns an ExplorationVerdict:

    Verdict Edge added? Callee analyzed?
    EXPLORE_METHOD (default) yes yes
    STOP_AFTER_CALL yes not via this edge
    STOP no no 
     1
 2

    VirtualCallResolver resolver =
    (caller, callee, stmt) -> {
      String targetClass = callee.getDeclClassType().getClassName();
      if (targetClass.equals("Hexagon")) {
        return ExplorationVerdict.STOP; // no edge at all
      }
      if (targetClass.equals("Triangle")) {
        return ExplorationVerdict.STOP_AFTER_CALL; // edge, but callee is not expanded
      }
      return ExplorationVerdict.EXPLORE_METHOD; // edge, callee is expanded (default)
    };

CallGraph cg =
    CallGraphConfig.builder()
        .view(view)
        .entryPoints(List.of(mainMethod))
        .virtualCallResolver(resolver)
        .cha()
        .build()
        .computeCallGraph();

    The default is VirtualCallResolver.all(). SuppressClinitCallResolver and AppOnlyClinitCallResolver handle static initializers, see the next section. Both take an optional second resolver, which decides about all other targets:

    1

    (caller, callee, stmt) ->
        callee.getDeclClassType().getClassName().equals("Helper")
            ? ExplorationVerdict.STOP
            : ExplorationVerdict.EXPLORE_METHOD;
// first drop JDK <clinit>s, then ask noHelper about everything else
VirtualCallResolver resolver = new AppOnlyClinitCallResolver(view, noHelper);

  public static void main(String[] args) throws Exception {
    Registry.register(); // runs Registry.<clinit> first

    Runnable task = () -> Helper.work(); // invokedynamic: lambda
    task.run();

    Plugin plugin = (Plugin) Class.forName("MyPlugin").newInstance(); // reflection
    plugin.start();
  }

    1

  static {
    init(); // static initializer: Registry.<clinit>
  }

  static void init() {}

  static void register() {}

    Registry.register() triggers Registry.<clinit>, and the algorithm finds this call while it walks through main. App.<clinit> is different: the JVM runs it before main, so no statement in the program calls it. seedEntryPointClinits(true) adds the <clinit> of each entry point's class as an extra root.

    Together, the seed flag and the virtualCallResolver reproduce the four classic <clinit> modes of Soot and Qilin:

    Mode seedEntryPointClinits virtualCallResolver App.<clinit> Registry.<clinit> JDK <clinit>s (e.g. Class.<clinit>)
    FULL true new SuppressClinitCallResolver(view) yes – –
    ON_THE_FLY false VirtualCallResolver.all() – yes yes
    APP false new AppOnlyClinitCallResolver(view) – yes –
    NONE false new SuppressClinitCallResolver(view) – – –

    CHA, RTA and Spark default to true + all(), so they include all of them. Qilin defaults to ON_THE_FLY.

    reflectionModel: reflection

    In general, static analysis can't know which class Class.forName("MyPlugin") loads. With the default, ReflectionModel.none(), reflective calls are treated as ordinary library calls, so in the example above MyPlugin.<init>() is never reached:

    ReflectionModel is a functional interface, so you can wrap a model or write your own. A model must return the same body every time it is asked about the same method: CHA, RTA, Spark and Qilin may ask more than once. To model more reflective APIs, extend AbstractReflectionModel. It finds the reflective calls, caches the rewritten bodies, and calls one hook per API (transformClassForName, transformMethodInvoke, ...).

    (method, body) ->
        view.getClass(method.getDeclaringClassType())
                .map(SootClass::isApplicationClass)

    Lambdas and method references compile to invokedynamic. The default resolver, DynamicInvokeResolver.bootstrapMethodHandles(), reads the target method from the bootstrap arguments. A lambda body (lambda$main$0) is reached through the functional object: in the example, task.run() calls it.

    Limits: reflection, invokedynamic and static initializers

    A call graph is only as complete as its model of the program. Calls that don't appear in the bytecode need extra help:

    • Reflection: reflectionModel.
    • Lambdas and method references: dynamicInvokeResolver.
    • Static initializers: seedEntryPointClinits.
    • Native methods: Qilin models a fixed set of JDK natives. CHA, RTA and Spark treat them as calls without a body.
    • Code that isn't in the view, e.g. callbacks from a framework: add the callback methods as entry points, or use RTA's preInstantiatedClasses.
